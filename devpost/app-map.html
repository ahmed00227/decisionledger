DecisionLedger — App Map

Snapshot of the proof of concept: record architectural decisions with machine-checkable criteria, paste PHP, get explainable offline findings. Analyzes pasted text only.

Main pieces

  • UI (Blade) — Overview, decisions, Check PHP, in-place review.
  • Thin HTTP controllers — validate input, orchestrate persistence.
  • Checker domain — tokenizer rule for direct Eloquent/DB calls in *Controller classes.
  • SQLite — decisions, criteria, check runs, findings (immutable checker status + separate workflow).

One action through the system

Action: Run Check PHP on a pasted controller → confirmed finding with evidence lines.

Reference route (2–3 stops)

Reference route for reuse — not claiming you walked it live in a guided tour.

1. Entry — app/Http/Controllers/CheckController.php · store

Validates paste, creates a new check run via RunPhpCheck, keeps prior runs.

2. Logic — app/Services/Checking/Rules/NoDirectEloquentInControllerRule.php · evaluate

Tokenizer scan; ignores comments/strings; confirmed only for supported direct calls inside *Controller method bodies.

3. Evidence — tests/Unit/Services/Checking/PhpArchitectureCheckerTest.php

Matrix: violating (evidence line), compliant, ambiguous (never confirmed), incomplete, DB facades, unknown rule keys.

To change this, start here

  • Widen/narrow detection allowlists → NoDirectEloquentInControllerRule.php (QUERY_METHODS, DB_FACADE_NAMES).
  • Demo paste buttons / fixtures → CheckController::demoSamples() + database/fixtures/php/.
  • Seeded decision copy / limitations → database/seeders/DatabaseSeeder.php.
  • Review must not mutate checker status → CheckController::review + FindingReviewTest.

A practice to reuse

When an agent (or you) claims a checker “understands architecture,” demand a narrow rule, fixtures for violating / compliant / ambiguous, and a test that treats false confirmed on ambiguous input as a release blocker. Evidence: devpost/spec.md rule section + PhpArchitectureCheckerTest.
